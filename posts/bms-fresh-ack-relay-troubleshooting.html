Cached BMS 상태를 새 ACK로 오인:
릴레이 조기 ON 차단

CAN 프레임을 받았다는 사실만 확인하지 않고, START 이후 새 승인 프레임이 도착한 뒤 실제 PE11 출력이 켜졌는지 시간 순서로 증명했습니다.

01 위험 시나리오

EVSE가 이전에 수신한 charge_permit=1 값을 보관한 상태에서 새로운 START 요청이 발생하면, 오래된 BMS 상태를 이번 요청에 대한 ACK로 오인할 가능성이 있었습니다.

통신 자체가 정상이어도 이벤트 순서가 잘못되면 릴레이가 너무 일찍 켜질 수 있습니다. 따라서 “필드 값이 1인가”가 아니라 “이번 요청 이후 새로 받은 값인가”를 판단해야 했습니다.

금지 조건

START 이전에 수신한 cached 0x100만으로 PE11을 ON해서는 안 됩니다.

02 안전 시퀀스 정의

Time ─────────────────────────────────────────────►

EVSE    START ── 0x201 Charge Request ─────────────
BMS                         └─ 0x100 Fresh ACK ────
EVSE                                           └─ PE11 ON
  1. START 입력을 감지합니다.
  2. EVSE가 0x201 Charge Request를 송신합니다.
  3. 요청 이후에 도착한 새로운 BMS 0x100만 ACK 후보로 인정합니다.
  4. charge_permit=1과 BMS State가 CHARGE_READY 또는 CHARGING인지 확인합니다.
  5. 모든 조건이 만족된 뒤 EVSE Relay PE11을 ON합니다.

프레임 Freshness 판정

bms_has_acknowledged()C
static bool bms_has_acknowledged(
    const evse_status_t *status)
{
    const bool accepted_state =
        status->bms.bms_state == CAN_BMS_STATE_CHARGE_READY ||
        status->bms.bms_state == CAN_BMS_STATE_CHARGING;

    return status->bms.online &&
           status->bms.charge_permit &&
           status->charge_request_transmitted &&
           status->bms.rx_sequence !=
               status->charge_request_rx_sequence &&
           accepted_state;
}

03 HIL Oracle: 통신 상태와 물리 출력 분리

먼저 CAN trace에서 Request, Fresh ACK, Relay command가 순서대로 발생했는지 검증했습니다.

CAN 시간 순서 검증PYTHON
request = wait_for_frame(id=0x201, value=1)
ack = wait_for_frame(id=0x100, after=request.timestamp)
relay = wait_for_frame(id=0x200, relay_on=True,
                       after=ack.timestamp)

assert request.timestamp < ack.timestamp < relay.timestamp

하지만 0x200 relay=1은 실제 접점 피드백이 아니라 소프트웨어 명령입니다. CAN 판정과 독립적으로 OpenOCD를 통해 GPIOE ODR의 PE11 bit를 확인했습니다.

PE11 물리 출력 교차 검증PYTHON
gpioe_odr = openocd.read_word(0x40021014)
assert gpioe_odr & (1 << 11)

Timeout 안전 복귀

BMS 프레임을 의도적으로 차단한 뒤, 정의된 시간 안에 릴레이 출력이 실제 LOW로 복귀하는지 확인했습니다.

Safe-off OraclePYTHON
assert 500.0 <= safe_off_elapsed_ms <= 650.0
assert gpioe_odr & (1 << 11) == 0

04 재발 방지

  • Cached state와 fresh ACK를 Sequence로 분리
  • Request·ACK·Relay의 timestamp 순서 검사
  • CAN software status와 실제 GPIO를 독립 Oracle로 검증
  • BMS/EVSE 통신 차단 자극과 복구 절차를 시험 명세에 포함
  • Actuation 시험은 Hard Interlock 승인 후에만 실행

검증 기준의 변화

“CAN 통신 성공”에서 “이번 요청 이후의 승인 + 올바른 상태 + 실제 출력 + Timeout 복귀”로 안전 판정 기준을 확장했습니다.
