OTA 전원 차단 시험:
임의의 PASS 기준을 만들지 않은 이유

구현된 무결성 보호와 아직 승인되지 않은 복구 정책을 구분하고, 시험을 실행할 수 있다는 이유만으로 제품 PASS를 선언하지 않은 판단 기록입니다.

01 구현된 보호

CoAP Block2 Download
  → Bank2 Staging
  → Size / CRC32 / Vector 검증
  → Relay OFF
  → Backup SRAM 요청
  → Reset
  → Bootloader Copy
  → Vector Table Last Commit
  → Application Jump

Bootloader는 전체 검증이 끝나기 전까지 Application Vector Table을 Flash에 기록하지 않습니다. 전송이 중단되거나 이미지가 손상되면 실행 가능한 시작점 자체를 만들지 않는 구조입니다.

Vector-last commitC
if (calculated_crc32 != expected_crc32)
    return CRC_MISMATCH;

if (!pending_vector_is_valid())
    return INVALID_VECTOR;

/* 전체 검증 성공 후 Vector Table 최종 기록 */
storage_write(0U, pending_vector_table, 8U);

       │
       ├─ Size
       ├─ CRC32
       └─ Vector validation
              │ PASS
              ▼

              ▼

02 Fault Injection 범위

  • UART Packet CRC16 오류 → NACK
  • 잘못된 DATA Offset → 수신 거부
  • 전체 Image CRC32 불일치 → 설치 거부
  • 잘못된 MSP 또는 Reset Handler → 실행 거부
  • 실패 후 Recovery Image 재설치

검증할 수 있었던 것

손상되거나 구조적으로 유효하지 않은 이미지의 설치·실행 차단은 명확한 입력과 Oracle로 시험할 수 있었습니다.

03 발견한 요구사항 Gap

전원 차단 자체는 주입할 수 있었지만, 차단 이후 어떤 상태를 정상 복구로 볼지 승인된 정책이 없었습니다.

  • A/B 이미지 구성
  • 이전 정상 버전 자동 롤백
  • Boot 실패 횟수 기반 복구
  • 전원 차단 이후 중단 위치 자동 재개
  • Signed Manifest와 ECU Identity
  • Anti-rollback 정책

시험 가능 ≠ 판정 가능

전원을 끊고 다시 켤 수 있다는 것과, 그 결과를 PASS/FAIL로 판정할 수 있다는 것은 별개입니다. 승인된 기대 상태와 복구 시간이 없으면 독립 Oracle이 성립하지 않습니다.

04 QA 판단

승인되지 않은 Oracle 차단PYTHON
pytest.skip(
    "GAP_REQUIREMENT: boot-failure count, "
    "rollback image, and power-loss recovery "
    "oracles are not approved"
)

이를 제품 PASS 또는 FAIL로 만들지 않고 GAP_REQUIREMENT로 등록했습니다. 구현된 Vector-last 보호를 과소평가하지 않되, A/B 롤백과 전원 복구 정책까지 완성된 것처럼 표현하지 않았습니다.

다음 승인 항목

복구 대상 이미지, 허용 Boot 실패 횟수, 전원 복귀 후 최대 복구 시간, 롤백 버전 정책, Signed Manifest와 ECU Identity를 요구사항으로 먼저 확정해야 합니다.
