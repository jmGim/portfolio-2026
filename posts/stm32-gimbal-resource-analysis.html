01 왜 리소스 예산을 따로 분석했나

3축 짐벌은 MPU6050 50Hz 샘플을 기준으로 20ms 안에 센서 수집, 자세 계산과 PWM 갱신을 마쳐야 합니다. 정상 동작만 확인하면 다음 성능 문제에서 연산, 통신, 스케줄링 중 무엇을 먼저 바꿔야 할지 결정할 수 없습니다.

따라서 두 가지를 숫자로 고정했습니다.

  1. 시간 예산 — I2C wire time과 FPU 연산 시간이 20ms 중 얼마를 사용하는가?
  2. 메모리 예산 — 512KB Flash에서 실행 이미지와 다운로드 이미지를 어떻게 격리할 것인가?

분석 조건

System Clock 84MHz, I2C Standard Mode 100kHz, MPU6050 14-byte burst read, HMC5883L 6-byte burst read 조건입니다.

02 Orchestrator와 의존성 방향

초기에는 센서, 서비스와 CLI 모듈이 서로의 헤더를 참조하면서 원형 의존성이 생기기 쉬웠습니다. 이를 해결하기 위해 최상위 ap.c가 실행 순서와 데이터 전달을 조율하는 Orchestrator 역할을 담당하도록 변경했습니다.

                         ap.c
                    [Orchestrator]
                  호출 순서 · 상태 조율
                    /            \
                   ▼              ▼
        gyro.c / mag.c      imu_service.c
        [Sensor Driver]     [Pure Calculation]
                   \              /
                    ▼            ▼
                   gimbal_control.c
                   [Actuation Service]

의존성 방향: Application → Service → Driver
금지: Driver ↔ Service 상호 include
  • Driver는 레지스터 접근과 Raw data 반환만 담당
  • Service는 입력 구조체를 받아 보정·융합하고 결과를 반환
  • CLI는 Application API를 통해 상태를 조회하며 Sensor Driver를 직접 호출하지 않음
  • 모듈별 테스트와 센서 교체 시 변경 범위를 계층 내부로 제한

03 STM32F411 512KB OTA Flash Partition

외장 저장장치 없이 새 펌웨어를 먼저 수신하기 위해 실행 영역과 Download Slot을 물리적으로 분리했습니다. 주소는 STM32F411의 sector 경계에 맞췄습니다.

Sector 0
Active App · 240KiB0x08004000–0x08040000
Sectors 1–5
Download Slot · 256KiB0x08040000–0x08080000
Sectors 6–7

정확한 안전성 경계

별도 Download Slot은 다운로드 도중 기존 Application을 보호하지만, 이것만으로 완전한 A/B 자동 롤백이 되는 것은 아닙니다. 복사 중 전원 차단 복구와 Boot 실패 정책은 별도 요구사항과 Oracle이 필요합니다.

04 20ms 제어 루프 Timing Breakdown

I2C 100kHz에서는 ACK를 포함한 1 byte 전송에 최소 9 clock, 즉 약 90µs가 필요합니다. Address와 register phase를 포함한 transaction byte 수를 기준으로 wire time을 산정했습니다.

I2C wire-time 계산TEXT
1 byte = 9 bits / 100,000 bits/s = 90 µs

MPU6050: 18 bytes × 90 µs = 1.62 ms
HMC5883L: 10 bytes × 90 µs = 0.90 ms
I2C total                  = 2.52 ms

2.52 ms / 20 ms × 100     = 12.6%

해석 시 주의

2.52ms는 명시된 byte 수를 이용한 이론적 wire-time입니다. HAL 호출, Task wake-up과 bus 상태 대기까지 포함한 실제 worst-case는 로직 애널라이저와 RTOS trace로 별도 측정해야 합니다.

05 데이터가 바꾼 설계 판단

상보 필터와 짐벌 제어 계산은 0.02ms 미만으로 관측된 반면, 두 센서의 I2C wire-time은 2.52ms였습니다. 이 조건에서는 수식 몇 줄을 줄이는 것보다 Serial Bus를 개선하는 편이 더 직접적입니다.

개선 후보기대 효과검토 사항
I2C Fast Mode 400kHzwire-time 이론상 최대 1/4센서 지원, pull-up, 배선 정전용량과 파형 검증
SPI 센서 전환더 높은 대역폭과 full-duplex 선택지핀 수, Driver 변경, 신규 H/W 영향
DMA 또는 비동기 I/OCPU blocking 시간 감소완료 ISR, buffer lifetime, Task 동기화 복잡도
수학 연산 미세 최적화현재 조건에서는 제한적정확도 손실 대비 얻는 시간이 작음

우선순위

측정 근거에 따라 “연산 코드 최적화”보다 “버스 속도·통신 방식·비동기 처리”를 다음 개선 후보로 선정할 수 있습니다.

06 고찰: 정상 동작에서 설명 가능한 설계로

이 프로젝트에서 얻은 가장 큰 교훈은 감각적인 튜닝보다 예산을 먼저 수치화해야 한다는 점입니다. 시간과 주소는 명확한 경계를 제공하며, 그 경계를 코드와 시험 항목으로 옮기면 설계 판단을 재현할 수 있습니다.

  • 의존성 — Orchestrator를 기준으로 호출 방향을 한쪽으로 제한
  • 시간 — 20ms Deadline을 통신·연산·잔여 Budget으로 분해
  • 메모리 — Linker 주소와 OTA 쓰기 대상을 sector 경계로 분리
  • 안전성 — 구현된 staging 보호와 미구현 A/B rollback을 구분
