01 현상

Raspberry Pi에서 Seeed USB-CAN 장치가 정상적으로 열렸지만 BMS·EVSE의 주기 CAN 프레임은 한 건도 수신되지 않았습니다.

수집 로그TEXT
CAN adapter opened
Selected channel: /dev/ttyUSB0
Expected: 0x100, 0x200 periodic frames
Actual: 0 frames

처음에는 BMS 또는 EVSE 펌웨어 결함처럼 보였습니다. 하지만 bitrate, CAN-H/CAN-L 배선, 종단저항, USB serial channel, backend, stale frame, 실제 Flash 이미지 중 어느 하나만 잘못되어도 같은 현상이 나타납니다.

핵심 위험

프레임이 없다는 관찰은 “제품이 프레임을 보내지 않았다”는 증거가 아닙니다. 수신 경로가 유효하다는 독립 증거가 먼저 필요합니다.

02 분석 순서와 원인 분리

제품과 시험환경을 섞어 판단하지 않도록 확인 순서를 고정했습니다.

  1. 전원 OFF 상태에서 종단저항 확인 — CAN-H와 CAN-L 사이의 합성 저항을 측정합니다.
  2. USB 장치 매핑 확인 — Fixture ID와 실제 /dev/ttyUSB*를 대응시킵니다.
  3. backend와 serial baud 확인 — Seeed 전용 backend와 2,000,000 baud를 명시합니다.
  4. CAN bitrate 적용값 확인 — BMS·EVSE와 동일한 500 kbit/s인지 metadata로 남깁니다.
  5. stale buffer 제거 후 passive 수집 — 이전 실행 데이터가 판정에 섞이지 않게 합니다.
  6. 주기와 CAN ID 판정 — 0x100, 0x200의 존재뿐 아니라 기대 주기까지 확인합니다.

Seeed backend 명시

Seeed USB-CAN은 SocketCAN의 can0가 아니라 python-can의 seeedstudio backend를 사용해야 했습니다.

Adapter 설정과 stale frame 제거PYTHON
bus = can.Bus(
    interface="seeedstudio",
    channel="/dev/ttyUSB0",
    baudrate=2_000_000,
    bitrate=500_000,
    timeout=0.1,
)

while bus.recv(timeout=0.0) is not None:
    pass  # 이전 실행의 stale frame 제거

03 재발 방지

  • CAN backend와 channel을 자동 추측하지 않고 명시적으로 선택
  • SocketCAN/Seeed 자동 fallback 제거
  • 실제 적용된 bitrate·baudrate·channel을 시험 metadata에 기록
  • HIL 실행 전 USB mapping preflight 추가
  • 0-frame 또는 실행 0건을 PASS로 바꾸지 못하도록 차단
실행되지 않은 시험 차단PYTHON
if tests == 0 or tests == skipped:
    print("BLOCKED_INFRA: no executed HIL test")
    return 4

04 QA 판단

시험환경이 정상임을 입증하기 전에는 제품 Fault를 판정할 근거가 없습니다. 따라서 공식 HIL 재시험 전까지 결과를 BLOCKED_INFRA로 유지했습니다.

완료한 것

시험환경 설정의 표준화, 실제 적용 파라미터의 증적화, 실행 0건 오판 방지 로직까지 완료했습니다.

완료했다고 말하지 않은 것

공식 Bench에서 재시험하기 전까지 프레임 수신 문제가 해결됐다고 과장하지 않고 “공식 재시험 대기” 상태로 관리했습니다.
