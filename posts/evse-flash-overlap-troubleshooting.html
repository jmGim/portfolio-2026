EVSE Application과 OTA Staging 중첩:
Linker Layout을 CI에서 차단

01 현상

EVSE Linker Script에서 Application이 OTA Staging 영역까지 포함하는 구조적 충돌을 발견했습니다.

충돌 전 설정TEXT
Application:
  ORIGIN = 0x08020000
  LENGTH = 1920K
  END    = 0x08200000

OTA Staging:
  START  = 0x08100000

현재 바이너리가 작으면 즉시 드러나지 않지만, Application이 커지면 Staging 이미지를 침범하거나 OTA 다운로드 중 실행 이미지를 손상할 수 있습니다.

왜 기능시험보다 먼저 막아야 하나

메모리 영역 중첩은 특정 기능의 실패가 아니라, 이미지 크기에 따라 제품 전체를 손상시킬 수 있는 배치 오류입니다.

02 원인

전체 2 MiB Flash에서 Bootloader 128 KiB만 제외해 Application 크기를 계산했습니다. 그 결과 OTA Staging 896 KiB와 Reserved 128 KiB가 Application 길이에서 차감되지 않았습니다.

잘못된 계산
2 MiB Total − 128 KiB Bootloader = 1920 KiB Application
                                  └─ Staging + Reserved 침범

필요한 계산
2 MiB Total − Bootloader − Staging − Reserved = 896 KiB Application

03 정상 Memory Map과 수정

0x08000000 ┌─────────────────────┐
           │ Bootloader 128 KiB  │
0x08020000 ├─────────────────────┤
           │ Application 896 KiB │
0x08100000 ├─────────────────────┤
           │ OTA Staging 896 KiB │
0x081E0000 ├─────────────────────┤
           │ Reserved 128 KiB    │
0x08200000 └─────────────────────┘

FLASH (rx) : ORIGIN = 0x08020000, LENGTH = 896K

수정 기준

Application의 끝 주소를 OTA Staging 시작 주소와 정확히 맞춰 0x08100000에서 경계를 닫았습니다.

04 CI Gate와 결함 종료 조건

Linker Script 한 파일의 수정만 믿지 않고, CI가 생성된 ELF/BIN의 실제 범위를 검사하도록 했습니다.

Artifact layout assertionsPYTHON
assert flash_origin == 0x08020000
assert flash_end == 0x08100000
assert binary_size <= 0xE0000
  • Linker ORIGIN과 END가 승인된 Memory Map과 일치하는지 확인
  • BIN 크기가 896 KiB를 넘지 않는지 확인
  • 제품 Source SHA, ELF/BIN SHA-256, 주소·크기를 Manifest에 기록
  • 작업 브랜치에 수정이 있어도 QA 승인 SHA와 Manifest가 PASS하기 전에는 결함을 종료하지 않음

교훈

Flash 안전성은 “현재 바이너리가 들어간다”가 아니라 “앞으로 커져도 승인된 영역을 넘을 수 없다”로 검증해야 합니다.
