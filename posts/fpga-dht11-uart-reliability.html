01 Repository Audit 범위

분석 대상은 포트폴리오에 등록된 Verilog_2026 / 18.smart_air_conditioner 저장소입니다. 현재 커밋 9a0aaee와 직전 통합 커밋 68d454e를 비교했습니다.

수치에는 세 가지 등급을 적용했습니다.

  1. RTL 확인 — 현재 코드에서 상태 수, Timeout, byte index처럼 직접 셀 수 있는 값
  2. Commit Diff — 이전·현재 코드의 실제 변경으로 입증되는 개선
  3. 추가 검증 필요 — Vivado timing/utilization report가 있어야 확정할 수 있는 값

사용하지 않은 수치

저장소에 post-route timing report가 없으므로 -5.2ns → +3.8ns, data path 15.2ns → 6.2ns, 지연 59.2% 개선은 확정 성과로 사용하지 않았습니다.

02 Single-wire를 위한 Open-Drain과 CDC

DHT11은 한 선을 FPGA와 센서가 번갈아 구동합니다. FPGA가 논리 High를 직접 밀어 넣으면 센서가 Low를 구동하는 순간 출력 충돌이 생길 수 있으므로, FPGA는 Start 구간에만 Low를 구동하고 나머지 시간에는 High-Z로 라인을 놓습니다.

Open-Drain 형태의 3-State 제어VERILOG
reg dht_drive;

// 1: FPGA가 LOW 구동, 0: High-Z로 release
assign dht11_data = dht_drive ? 1'b0 : 1'bz;

Constraint에는 DHT11 pin의 Pull-up도 지정되어 있습니다. High-Z일 때 라인이 정의된 High로 복귀하도록 RTL과 I/O constraint가 함께 구성됩니다.

100MHz Domain으로 들어오는 비동기 신호

센서 Edge는 FPGA clock과 위상이 무관합니다. 현재 커밋은 입력을 2개의 Flip-Flop에 순차 통과시킨 뒤 Edge를 검출합니다. 이는 Metastability가 FSM까지 전파될 가능성을 낮추는 표준 CDC 패턴입니다.

2-Stage Synchronizer + Edge DetectorVERILOG
always @(posedge clk or posedge reset) begin
    if (reset) begin
        d1_data <= 1'b1;
        d2_data <= 1'b1;
    end else begin
        d1_data <= dht11_data;
        d2_data <= d1_data;
    end
end

wire falling_edge = (d2_data == 1'b1 && d1_data == 1'b0);
wire rising_edge  = (d2_data == 1'b0 && d1_data == 1'b1);

정확한 표현

2-Stage Synchronizer는 Metastability 위험을 낮추지만 임의 길이의 glitch를 “완전히 제거”하는 필터는 아닙니다. 필요하면 pulse-width qualification을 별도로 추가해야 합니다.

03 DHT11 FSM: 멈추지 않는 시간축과 5개 Timeout

현재 RTL은 100MHz를 1µs tick으로 분주하고, 하나의 r_wait_cnt가 계속 증가하도록 구성합니다. 상태 전이 또는 Edge 시점에만 값을 읽고 0으로 초기화합니다.

40-bit Checksum Gate

40개 bit를 수신한 뒤 네 data byte의 합과 checksum byte가 일치할 때만 Humidity·Temperature register를 갱신하고 data_valid를 한 clock 동안 발생시킵니다.

Invalid frame의 UART 전파 차단VERILOG
if ((r_dht_data_reg[39:32] + r_dht_data_reg[31:24]
   + r_dht_data_reg[23:16] + r_dht_data_reg[15:8])
    == r_dht_data_reg[7:0]) begin
    humidity    <= r_dht_data_reg[39:32];
    temperature <= r_dht_data_reg[23:16];
    data_valid  <= 1'b1;
end

04 UART Commit Diff: 실제로 고쳐진 두 오류

1. 16 data bit를 보내던 Framing 오류

이전 TX는 8-bit 입력을 16-bit r_data_reg에 담고 r_bit_cnt >= 15까지 전송했습니다. Start와 Stop 사이에 16개 data bit가 나가므로 표준 8N1 수신기와 framing이 맞지 않습니다. 현재 코드는 bit 0~7만 송신합니다.

이전 문자
18 bit
현재 8N1
10 bit

문자당 framing bit 수는 18→10으로 줄어 44.4% 감소했습니다. 이는 timing slack 개선이 아니라 프로토콜 framing 정정으로 입증되는 수치입니다.

2. TX에 적용된 RX용 16× Oversampling

Baud divider 변경DIFF
// Before: TX가 목표보다 16배 빠른 tick 사용
DIVIDER_CNT = 100_000_000 / BPS / 16;

// After: TX는 bit마다 1 tick
DIVIDER_CNT = 100_000_000 / BPS;

현재 integer divider는 10,416 clock이며 실제 tick은 약 9,600.6Hz입니다. 9,600bps 대비 오차는 약 +0.0064%입니다. RX에는 별도로 16× oversampling divider가 유지됩니다.

6개 Field Snapshot → 117-byte Frame

data_sender는 TX가 idle일 때 Current Time, Alarm Time, Target Temp, Current Temp, Humidity, Fan Speed를 동시에 latch합니다. 이후 uart_tx가 index 0~116을 순회하므로 전송 중 센서 값이 바뀌어도 한 frame 안의 데이터는 동일 시점 snapshot을 유지합니다.

Nominal wire-timeTEXT
117 bytes × 10 bits / 9,600 bps = 121.875 ms

121.875 ms / 3,000 ms × 100 = 4.0625%

Source-derived 결과

117-byte frame은 8N1·9600bps 기준 약 121.875ms 동안 선로를 사용하며, 3초 DHT11 trigger 주기 대비 약 4.06%입니다.

05 BCD 경로와 Timing Claim Audit

현재 uart_tx.v의 Target/Current Temperature와 Humidity 2자리 변환은 /10, %10 대신 범위 비교와 뺄셈을 사용합니다. 이 부분은 실제 소스에서 확인됩니다.

온습도용 비교·뺄셈 BCDVERILOG
wire [3:0] h_10 =
    (h_adj >= 90) ? 9 : (h_adj >= 80) ? 8 :
    (h_adj >= 70) ? 7 : (h_adj >= 60) ? 6 :
    (h_adj >= 50) ? 5 : (h_adj >= 40) ? 4 :
    (h_adj >= 30) ? 3 : (h_adj >= 20) ? 2 :
    (h_adj >= 10) ? 1 : 0;
wire [3:0] h_1 = h_adj - (h_10 * 10);

하지만 저장소 전체에서 나눗셈을 완전히 제거한 것은 아닙니다.

  • uart_tx.v: Current/Alarm Time의 /100, %100
  • fnd.v: 4-digit 변환의 /10, /100, /1000, %10
  • 상수 parameter 계산은 합성 시 상수화되지만, data path 연산은 별도 timing 확인 필요

Slack 수치를 확정하지 않은 이유

프로젝트에는 .rpt, routed checkpoint 또는 timing summary가 없습니다. 따라서 10ns constraint만으로 실제 WNS, TNS와 Critical Path를 단정할 수 없습니다.

다음 리포트에서 확인할 항목

Vivado evidence commandsTCL
report_timing_summary -delay_type max -max_paths 10 \
  -file reports/timing_summary.rpt

report_utilization -hierarchical \
  -file reports/utilization_hier.rpt

개선 전후 동일 constraint와 동일 top으로 WNS/TNS, Data Path Delay, LUT/FF 사용량을 저장해야 그때 비로소 Slack과 면적 개선률을 포트폴리오 수치로 사용할 수 있습니다.

고찰

FPGA 포트폴리오의 신뢰성은 “파형이 나왔다”는 설명보다, RTL 구조·commit diff·testbench·post-route report를 하나의 증거 체계로 연결할 때 높아집니다. 이번 분석에서는 확인된 개선을 강조하면서도 아직 생성하지 않은 timing 수치를 의도적으로 제외했습니다.
