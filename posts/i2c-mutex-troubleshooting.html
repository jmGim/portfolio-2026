01 개요

FreeRTOS 기반 3축 짐벌 프로젝트에서 MPU6050(자이로/가속도)과 HMC5883L(지자기) 두 센서를 동일 I2C1 버스에서 제어할 때, 간헐적으로 I2C 버스가 멈추고 모든 HAL_I2C 함수가 HAL_BUSY를 반환하는 현상이 발생했습니다.

🎯 담당 역할

  • MPU6050 + HMC5883L I2C 드라이버 구현 및 RTOS Task 설계
  • I2C 버스 경합 문제 분석 및 Mutex 기반 동기화 설계
  • 오실로스코프를 이용한 SDA/SCL 파형 분석

🏗️ 시스템 구성

MCU
STM32F411RET6 (Cortex-M4F, 100MHz)
RTOS
FreeRTOS (CMSIS-RTOS2)
센서
MPU6050 (0x68), HMC5883L (0x1E)
버스
I2C1, 100kHz Standard Mode

02 설계 및 구현

📐 I2C 버스 공유 아키텍처

두 센서가 동일 I2C1 버스를 공유하며, 각각 별도의 FreeRTOS Task에서 독립적으로 읽기를 수행합니다.

⚙️ Task 설계

FreeRTOS Task 구성C
// freertos.c — Task 생성
osThreadNew(gyroSystemTask,  NULL, &gyroTask_attr);   // Normal3, 4096B
osThreadNew(magSystemTask,   NULL, &magTask_attr);    // Normal3, 2048B

// gyroSystemTask: Semaphore 대기 → MPU6050 I2C Read (50Hz)
// magSystemTask:  osDelay(10)   → HMC5883L I2C Read (100Hz)

🔧 MPU6050 초기화 시퀀스

gyro.c — Gyro_Init()C
bool Gyro_Init(void) {
  uint8_t val;

  // 1. Hardware Reset
  val = 0x80;
  HAL_I2C_Mem_Write(&hi2c1, MPU_ADDR<<1,
    PWR_MGMT_1, 1, &val, 1, 10);
  osDelay(100);

  // 2. PLL Clock Source (X-axis Gyro)
  val = 0x01;
  HAL_I2C_Mem_Write(&hi2c1, MPU_ADDR<<1,
    PWR_MGMT_1, 1, &val, 1, 10);

  // 3. DLPF 40Hz → CONFIG register
  val = 0x03;
  HAL_I2C_Mem_Write(&hi2c1, MPU_ADDR<<1,
    CONFIG, 1, &val, 1, 10);

  // 4. Sample Rate = 50Hz (1kHz / (19+1))
  val = 19;
  HAL_I2C_Mem_Write(&hi2c1, MPU_ADDR<<1,
    SMPLRT_DIV, 1, &val, 1, 10);

  // 5. Latch INT, Clear on Read
  val = 0x30;
  HAL_I2C_Mem_Write(&hi2c1, MPU_ADDR<<1,
    INT_PIN_CFG, 1, &val, 1, 10);

  return true;
}

03 트러블슈팅

🔍 증상

  • 두 센서를 동시에 읽을 때 간헐적으로 I2C 버스가 멈춤
  • HAL_I2C_Mem_Read()가 HAL_BUSY 반환 → 이후 모든 I2C 통신 불가
  • 오실로스코프: ACK 후 STOP 조건 없이 새 START 발생 확인

📊 원인 분석

FreeRTOS의 두 Task(gyroSystemTask, magSystemTask)가 동일 우선순위(Normal3)로 동일 I2C1 페리페럴에 접근. HAL 드라이버 내부의 Lock 플래그와 RTOS 컨텍스트 스위칭 타이밍이 충돌하여 경합 발생.

경합 발생 시나리오Text
Time ─────────────────────────────────────────►

gyroTask:  ┌─ I2C Read START ──── ACK ───┐
           │  (hi2c1.Lock = HAL_LOCKED)   │
           │                              │
magTask:   │      ↑ Context Switch!       │
           │      ├─ I2C Read START ─────►│ HAL_BUSY!
           │      │  (hi2c1.Lock 이미 LOCKED)
           │      │
           └──────┘  ← STOP 미발생 (버스 Hang)

✅ 해결: osMutex 기반 I2C 접근 보호

I2C Mutex PatternC
// hw.c — Mutex 생성
osMutexId_t i2c1_mutex;
void hwInit(void) {
  i2c1_mutex = osMutexNew(NULL);
}

// gyro.c — 센서 읽기 시 Mutex 보호
bool Gyro_Read(gyro_data_t *data) {
  osMutexAcquire(i2c1_mutex, osWaitForever);

  HAL_StatusTypeDef ret = HAL_I2C_Mem_Read(
    &hi2c1, MPU6050_ADDR << 1,
    ACCEL_XOUT_H, I2C_MEMADD_SIZE_8BIT,
    raw, 14, 50);   // Timeout 50ms

  osMutexRelease(i2c1_mutex);
  return (ret == HAL_OK);
}

// mag.c — 동일한 Mutex 적용
bool Mag_Read(mag_data_t *data) {
  osMutexAcquire(i2c1_mutex, osWaitForever);

  HAL_StatusTypeDef ret = HAL_I2C_Mem_Read(
    &hi2c1, HMC5883L_ADDR << 1,
    DATA_OUT_X_MSB, I2C_MEMADD_SIZE_8BIT,
    raw, 6, 50);

  osMutexRelease(i2c1_mutex);
  return (ret == HAL_OK);
}

📈 해결 결과

  • I2C Hang 현상 완전 해소 (48시간 연속 동작 테스트 통과)
  • HAL Timeout 50ms 설정으로 만약의 Hang에도 자동 복구
  • MPU6050 50Hz + HMC5883L 100Hz 갱신 주기 안정 유지

04 고찰 및 느낀점

💡 기술적 고찰

  • HAL 드라이버의 내부 Lock은 RTOS 환경에서 충분하지 않다. 반드시 osMutex 등 OS 레벨 동기화 메커니즘이 필요하다.
  • Priority Inheritance 옵션을 적용하면 우선순위 역전 문제도 동시에 예방할 수 있다.
  • 타이밍 문제는 로그만으로 재현이 어렵다. 오실로스코프로 SDA/SCL 파형을 직접 확인하는 것이 가장 정확한 디버깅 방법이다.

📝 느낀점

이 경험을 통해 '동작하는 코드'와 '신뢰할 수 있는 코드'의 차이를 체감했습니다. 단일 Task에서는 문제없이 동작하던 I2C 드라이버가 멀티태스킹 환경에서는 예측 불가능한 Hang을 일으켰고, 이를 해결하기 위해 HAL의 내부 동작을 레지스터 수준까지 추적해야 했습니다. 방산·자동차 도메인에서 요구하는 '신뢰성'은 바로 이런 세밀한 검증 과정에서 나온다는 것을 배웠습니다.
